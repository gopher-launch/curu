- Delivery: CDP-002
- Host/cluster boundary: the versioned single-node kind template and bounded scripts create fixed cluster `curu-local`, explicit context `kind-curu-local`, and namespace `curu-system` from required host storage, declared PV capacity, CPU, and memory inputs. Bootstrap claims only a new or empty dedicated real directory and refuses to mark a non-empty unowned directory; a valid marked directory remains reusable with retained data. This is laptop persistence, not backup or host-failure recovery.
- Local HTTPS inputs: stable `curu.test` and `identity.curu.test` names resolve on the host through an explicit managed hosts change and in-cluster through the delivered `curu-edge` Service. PKI preparation creates/reuses a host-held local CA, verifies both certificate names, uploads only the leaf TLS key/certificate and public CA, and provides explicit Ubuntu trust install/check/removal steps without disabling verification.
- Verification and qualification: static checks reject invalid resource/storage inputs, prove a non-empty unowned directory cannot be marked while an owned retained directory can be reused, and assert loopback exposure/retention. The disposable live check exercises two cluster creations, source image build/load and reload, expected Docker port/mount configuration, marker retention across pod and cluster recreation, and CA-verified HTTPS from both the host and a pod. NetworkPolicy enforcement remains unverified; the laptop administrator, Docker/kind node, and pod network are the trusted local boundary. CDP-002 alone did not establish database, issuer, gateway login, library access, LAN exposure, or target-laptop acceptance.

## Trusted JWT authentication

- Delivery: CURU-015
- Explicit profile: runtime configuration selects only the standard RFC 9068 OAuth JWT access-token profile. The adapter accepts the two access-token media types case-insensitively and validates their required claims without a generic-JWT or provider-specific fallback.
- Trust and validation: compact JWTs require canonical unpadded base64url protected-header, payload, and signature segments, valid UTF-8 JSON objects with well-formed Unicode strings and duplicate-free member names, understood critical headers, one non-empty key ID, an allowed `RS256` or `ES256` algorithm, an eligible unique JWKS key, a valid signature, exact issuer, the configured Curu resource audience, non-empty subject, numeric temporal claims, and bounded lifetime/skew. Unsigned, unencoded-payload, wrong-kind, wrong-purpose, malformed, expired, substituted-key, and untrusted tokens fail closed.
- Principal boundary: successful validation yields only the exact issuer/subject external identity. Tokens, provider claims, emails, display names, roles, and groups do not enter application or domain behavior.
- JWKS behavior: Curu fetches only the configured HTTPS endpoint with bounded time and response size, applies HTTP freshness precedence and overflow-safe current-age calculation with a five-minute default and 15-minute cap, supports planned overlap, rate-limits unknown-key refresh, and never extends an expired cache after failure. Ambiguous or invalid explicit freshness is treated as stale, while numeric age overflow saturates rather than becoming zero. A fresh cached known key remains usable during a refresh failure; otherwise the key dependency is unavailable.
- Runtime integration: authentication trust configuration is required before startup. Liveness remains process-only, while readiness requires a non-expired usable key set. Local generated signing/JWKS fixtures cover both media types, RSA and EC validation, required/wrong claims, invalid UTF-8 and malformed Unicode escapes in protected headers and claims, valid escaped Unicode pairs, unencoded payload, critical-header and noncanonical-segment rejection, trust failures, rotation, HTTP freshness/current age including numeric overflow, cache failure, refresh limiting, duplicate credentials, and unsupported-profile rejection.
- Subsequent delivery: CURU-016 adds browser/HTMX authentication outcomes, CSRF, origin, and proxy protections. No product routes, login, issuer, exchange, production signer, or provider adapter are added by CURU-015.

A session owns a title, optional date, group/context, intent, positive aggregate revision, and zero or more ordered named blocks. Each block owns freeform intent, notes, and an observation lens and can exist without any activity. No stage enum, recursive group, placement snapshot, or timing model is introduced.
- Explicit aggregate saves: the editor exposes saved/unsaved/error feedback and submits session fields plus the complete block list as one bounded form. Adding or removing a block only changes that open form until the owner explicitly saves. The repository first compares the owner-scoped current session revision, then replaces its ordered blocks in the same transaction; stale or failed saves leave authoritative content unchanged and re-render the complete submitted aggregate.
- Non-destructive lifecycle: current session detail pages provide revision-checked archive, while `/sessions/archived` provides the protected archive and explicit restoration under the same stable session UUID. Blocks remain stored through archive/restore and there is no permanent-delete path.
- Data and recovery: migration 5 adds `sessions` and `session_blocks`, and the restricted runtime role receives only required table DML. The application recovery manifest hashes every session/block field and the isolated restore fixture includes an archived session. Durable conflicting-session recovery remains assigned to CURU-025.
- Verification: focused domain and handler tests cover undated drafts, empty blocks, complete form parsing, validation, explicit saves, stale submitted-form preservation, no-activity detail rendering, and archive routing. The opt-in disposable PostgreSQL suite exercises migration/grants and the extended backup/restore manifest; no live database result is claimed when `CURU_TEST_DATABASE_URL` is unset.
