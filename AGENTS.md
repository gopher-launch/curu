# Curu contributor guidance

## Select the workstream

- Application work follows the root `roadmap.md` and its `CURU-` IDs. Deployment work follows `deploy/roadmap.md` and its `CDP-` IDs; `deploy/README.md` records the deployment design and implemented operator interfaces. Select one bounded Task from the intended roadmap; do not combine the two backlogs or assume an automation runner discovers the deployment roadmap automatically. Preserve every existing ID.
- The application owns product behavior, domain/use-case policy, HTTP behavior, configuration validation, schema migrations, initialization, and application recovery checks. Deployment owns Helm templates, kind bootstrap, component configuration, routing/TLS, identity-service integration, database provisioning, credentials, storage, and operator sequencing. An external database in the application architecture may be the bundled Postgres service in the deployment; it is still outside the Curu process.
- Keep deployment implementation under `deploy/`, with the chart at `deploy/helm/curu/`, kind configuration at `deploy/kind/`, and operator automation at `deploy/scripts/`. These paths are planned until their owning Tasks implement them. Shared files such as this guidance, the root README, and the Dockerfile may change when the selected Task requires it. Application source or contract changes discovered during deployment must be explicitly scoped and reconciled; do not silently widen a deployment Task into a product feature or weaken validation to fit a provider.
- Read the existing contracts relevant to either workstream: `doc/product-baseline.md` for product behavior, `doc/implementation-design.md` for architecture, and `doc/integration-contract.md` for JWT, authorization, browser-security, and data-service boundaries. Use `doc/configuration.md`, `doc/gateway.md`, `doc/database-operations.md`, and the root `README.md` for implemented configuration and executable commands. These are delivered baseline documents, not permission to implement their entire scope.
- Do not expand into later Tasks or use the old Curu prototype as an implementation source.

## Deployment policy

- Build and maintain the complete Helm chart in this repository. Define Curu, NGINX, OAuth2 Proxy, Keycloak, Postgres, and operator Jobs in owned templates; do not include vendor or other third-party subcharts or download them during bootstrap. Upstream container images are allowed and must be pinned to reviewed versions. Optional bundled services must support configured external equivalents and existing Secret references.
- The first target is the HP Ubuntu laptop with a single-node kind cluster, local HTTPS, and persistent laptop storage. Use plain NGINX as the chart-owned reverse proxy, OAuth2 Proxy for browser OIDC, Keycloak for identity, and cluster-local Postgres. No paid service, cloud account, hosted identity subscription, or cloud deployment is a prerequisite. Hosted Kubernetes is a future target, not current acceptance evidence.
- NetworkPolicy enforcement and its verification may be deferred when unavailable in kind. Do not make a replacement CNI or an isolation test a blocker for this local MVP. This is an explicit local-development qualification of the platform isolation expectations in `doc/gateway.md` and `doc/integration-contract.md`, not a change to application authentication or authorization. Expose only the intended edge, keep backend Services internal and readiness private, document the trusted local-cluster/private-hop boundary, and report enforcement as unverified until exercised. Do not claim ClusterIP Services prove pod isolation or carry this exception silently into a hosted environment.
- Keep runtime, migration, initialization, database administration, and identity administration authority separate. Ordinary Curu startup never migrates or seeds. Preserve the exact owner binding and stable internal owner UUID. Do not disable HTTPS/JWKS verification or accept ID tokens to get local login working.
- Scheduled backups and cloud backup storage are outside the first milestone. Manual export/isolated restore is an optional Task, not an installation prerequisite. Persistent storage is not proof of a backup or permission to reset retained data.

## Verification and reconciliation

- Source is the truth of implemented behavior; `capabilities.md` records application scope and provenance. Each roadmap records its own planning, readiness, and acceptance criteria. Distinguish accepted design, implemented interfaces, automated evidence, and actual operator/device outcomes. If these disagree materially, identify the discrepancy rather than silently redefining behavior.
- Keep dependencies pointing inward. HTTP, JWT/provider details, GORM, and deployment concerns belong at their respective boundaries; domain behavior must not depend on them. Introduce packages and schema only when the selected task needs them.
- For Go changes, run the documented mandatory suite, `go test ./...`, and verify the server builds with `go build ./cmd/curu`. Use focused tests and additional checks such as `go vet ./...` or `go test -race ./...` when relevant to the change. Documentation-only changes require consistency checks, not unrelated runtime tests. Verification must exercise the behavior claimed; do not report unperformed container, database, browser, or field checks as passed.
- For chart changes, run the deployment checks established by the owning Tasks: Helm lint/render and configuration rejection checks, followed by focused disposable-cluster checks where runtime behavior is claimed. Introduce exact commands with their implementation; this guidance does not imply a chart or deployment test runner already exists. Do not require the Go suite for deployment-only changes unless they also affect application behavior or builds.
- Implement and document new migration, bootstrap, database, or security commands with their owning tasks. Do not invent commands for absent functionality. Preserve explicit migrations, restricted runtime access, and the separation of startup, initialization, ordinary saves, and recovery.
- Product and deployment documents describe contracts and implemented interfaces. Keep run progress, review verdicts, pending integration and completion announcements in external records. Keep planning and readiness in the owning roadmap; use delivery IDs in `capabilities.md` for application provenance without claiming a deployment from application delivery alone.
- Reconcile affected contributor guidance, README commands, contracts, capabilities, and roadmap entries in the same candidate as the change. Remove obsolete bootstrap instructions rather than carrying them into subsequent tasks. Do not claim later features or validation outcomes prematurely.
- Chris owns material product choices. Make routine implementation and documentation decisions within the accepted task and contracts without approval questions. Material contract changes require an explicit product decision and corresponding documentation reconciliation. Resolve genuinely open questions, including template field policy and recovery-draft details, in their scoped tasks; do not reopen the delivered authentication/authorization contract unless a revision is authorized.
